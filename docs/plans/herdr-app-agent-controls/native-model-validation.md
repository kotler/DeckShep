# Native Model qualification

**Date** 2026-11-14  
**Status** Active Model remains unqualified for both delivery paths

The later [mod delivery experiment](herdr-mod-model-delivery-prototype.md)
demonstrated a real CLI Model change and held-helper refusals using existing
extensions. It is an owner-authorized feasibility prototype, not completion of
all production prerequisites below. Upstream changes are out of scope.

The existing isolated live suite qualifies App navigation and passive row 3
projection on the reviewed signed App 0.1.14/Core 0.1.19 pair. Its Codex and
Claude labels come from disposable OSC status programs. They are not provider
sessions. A successful run cannot establish a Codex settings change.

## Prerequisites for an active run

Before implementing a real Model adapter, the feasibility record must name a
supported interface proving the App's actual Core connection and the exact
terminal, foreground CLI process and root chat. It must provide continuous
focus and readiness revisions, including A → B → A, rather than just matching
client polls. Both candidates need recipient enforcement of authorization
retirement and the original press deadline before every effect. Native also
needs passive cursor/view evidence. API needs native-equivalent eligibility,
complete picker ordering, preserved effort and session-only application.

No inspected current interface supplies this combined mapping. P3 shared
authority work and active native qualification therefore remain gated. Do not
start a real Codex session merely to exercise an unconditional settings write.
Upstream interface changes require owner direction. The
[evaluation](delivery_evaluation.md) records the concrete missing capabilities.

## Owned launcher contract

Once a supported interface exists, extend the owned launcher with an exact
artifact manifest for App, Core, CLI and adapter. Give every process a private
HOME, separate socket namespace and explicit process/start identity. Create two
disposable root chats in the same folder and two owned Cores with colliding
local terminal addresses. Avoid inheriting provider credentials, owner hooks
or daemons. Any authenticated fixture session needs explicit authorization.

The committing authority must expose effect order, captured deadlines and
retirement acknowledgements without logging terminal content or prompts.
Cleanup must verify each process identity before signaling it, drain accepted
work, prove exit and check unchanged owner settings before deleting files.

Use the repository's current `ASW_LIVE` authorization rules. Historical logs
and artifact manifests are evidence only. Never attach to an existing owner
App, Core or agent and never install/restart Stream Deck as verification.

## Common run for each candidate

1. Capture the exact revisions, source mapping, route verification record and
   process/session binding. Confirm the initial empty composer or supported
   current-model picker and current effort from that CLI.
2. Through ordinary virtual Stream Deck key-down/key-up events, advance Model
   once. Independently read the resulting model and effort from the same root
   session. Verify unchanged other chat, draft and saved defaults. Include wrap,
   supported footerless composer and command-time footer transitions.
3. Repeat with an owned editor frontmost. Record macOS activation before,
   during and after the operation and count editor key events. Require the
   editor to retain focus with zero DeckShep input. Passive Model alone cannot
   satisfy this active positive case.
4. Hold work at the committing authority after the final client check. Change
   focus, switch away and back, start a turn, replace a CLI/chat, reconnect or
   present the colliding wrong Core. Release work before and after the original
   deadline. Count effects after draining the queue, including picker opens.
5. Hold a first effect, revoke consent or hide/remap the key outside the serial
   press queue, obtain closed acknowledgement, then release. Require zero
   effects. Also test commit-before-retirement and report partial completion.
6. Lose an apply reply or alter the view after a native write. Require inert
   uncertainty/quarantine, no automatic cleanup/retry/fallback, stable
   retirement identity across reconnects, and explicit read-only recovery.

Record supported and unsupported cases separately for each route. If neither
qualifies, retain informational Model and both documented delivery candidates.
If both qualify, present measured trade-offs for the owner's route choice.
